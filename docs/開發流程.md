# 開發流程(一張改動的一生)

本文件定義「夷問」專案從需求到上線的標準流程。所有功能修改都照這條路走。

```
回饋/需求 → 開 Issue → 排優先級與里程碑
→ 開分支 → 實作 → 照驗收標準自測(含迴歸測試)
→ 發 Pull Request → 合併回 main
→ 更新 CHANGELOG、打版本標籤 → 部署 → 線上驗證
→ 關閉 Issue
```

## 1. 開 Issue

- 每個問題/需求一張 issue,**不寫在腦袋裡、不直接動手改**
- 固定格式:現況、預期、來源(誰提的)、驗收標準
- 貼標籤:
  - 類型:`bug`(壞掉)/ `enhancement`(改善既有)/ `feature`(全新功能)
  - 優先級:`P1`(重要且急)/ `P2`(重要不急)/ `P3`(有空再做)
- 大功能(動到資料結構、對話邏輯)先寫 mini-PRD,放 `docs/prd/`,範本見
  [docs/templates/PRD-範本.md](templates/PRD-範本.md)

## 2. 開分支

- 一個分支只做一件事,命名:`fix/簡短描述`、`feat/簡短描述`、`docs/簡短描述`
- 例:`fix/input-placeholder-typo`、`feat/multi-turn-chat`

## 3. Commit 訊息(Conventional Commits)

```
fix: 修正輸入框「夷間志」誤植 (#3)
feat: 新增多輪對話支援 (#2)
docs: 補充部署文件
```

- 開頭用 `fix:` / `feat:` / `docs:` / `refactor:` / `chore:`
- 結尾帶 issue 編號 `(#N)`,GitHub 會自動把 commit 連到 issue

## 4. Pull Request

- 就算專案只有一個人,也發 PR 再合併——PR 描述是寫給三個月後的自己和下一屆接手的人看的
- PR 描述固定寫:改了什麼、為什麼、怎麼測的、關聯 issue(寫 `Closes #N` 可在合併時自動關單)

## 5. 測試

- 依 issue 的驗收標準自測
- 凡是動到 prompt、模型、檢索邏輯,**必跑**[迴歸測試清單](測試/迴歸測試清單.md)整輪,
  確認要修的有修好、改好的沒退步

## 6. 發版與部署

1. 合併回 `main` 後,把 CHANGELOG「未發布」區的內容移到新版本號下,標上日期
2. 打標籤:`git tag v1.1.0 && git push --tags`
3. SSH 進伺服器,於專案目錄執行:

   ```bash
   git pull
   sudo docker compose up -d --build
   ```

   (伺服器位置、金鑰等敏感資訊不放在公開 repo,見本機的部署文件)
4. 線上驗證:開 https://yijianzhi.org 實際測過驗收標準,才算完成
5. 關閉 issue,必要時回報老師

## 7. 重大技術決策

凡是「做了就很難回頭」的選擇(換模型、重切語料、換資料庫),寫一篇 ADR 放
`docs/adr/`,範本見 [docs/templates/ADR-範本.md](templates/ADR-範本.md)。
半頁就好,重點是記下**當時考慮過什麼、為什麼這樣選**。
