## 二、專案概要

「夷問」是可用中文問答南宋洪邁《夷堅志》的 RAG 聊天機器人。

```
使用者提問
  → (若有前文)改寫成完整問句
  → 到向量庫找最相關的 10 段原文
  → 把「系統規則 + 原文 + 對話歷史 + 問題」送給 OpenAI gpt-4o-mini
  → 串流回答,結尾附延伸問題按鈕
```

| 元件 | 用途 |
|---|---|
| Chainlit | 聊天網頁介面 |
| LangChain + OpenAI `gpt-4o-mini` | 生成回答 |
| Qdrant(內嵌式,`qdrant/` 資料夾) | 向量資料庫,存 312 段原文的向量 |
| `data_source/` | 原始 docx 與切好的 312 段 txt |

### 檔案地圖

| 檔案 | 內容 |
|---|---|
| `app.py` | **主程式,幾乎所有修改都在這裡** |
| `chainlit.md` | 首頁「說明」頁內容 |
| `public/custom.css` | 自訂樣式(複製鍵位置) |
| `.chainlit/config.toml` | Chainlit 介面設定 |
| `.chainlit/translations/zh-TW.json` | 介面中文字串 |
| `index.py` / `split.py` | 建向量庫 / 切文本(未修改) |
| `data_source/original/` | 原始文本 `yijian_zhi.docx` |
| `data_source/splitted/` | 切好的 312 個 txt |
| `qdrant/` | 向量資料庫(系統回答時只讀這裡) |
| `docs/` | 開發流程、範本、需求文件、測試清單、本文件 |
| `CHANGELOG.md` | 版本變更紀錄 |

## 三、本機怎麼跑

需要先安裝 Docker Desktop。

```bash
cp .env.example .env        # 然後填入你的 OPENAI_API_KEY
docker compose up -d --build
```

開啟 http://localhost:8000 。

| 指令 | 用途 |
|---|---|
| `docker compose up -d --build` | 改完程式後重建並重啟(**每次改完都要 `--build` 才會生效**) |
| `docker compose logs -f` | 即時看紀錄 |
| `docker compose logs \| grep 檢索問題改寫` | 看追問被改寫成什麼(除錯多輪對話用) |
| `docker compose down` | 停止 |

## 四、已完成的修改

修改源自老師 1150903 的回饋意見(共 7 點),GitHub issue 編號與回饋順序一致。

### #3 輸入框錯字「夷間志」

| | |
|---|---|
| 問題 | 輸入框提示文字寫成「詢問有關**夷間**志的疑問」 |
| 原因 | `.chainlit/translations/zh-TW.json` 的 `chat.input.placeholder` 打錯字 |
| 解決 | 改為「夷堅志」(檔案內中文以 `\uXXXX` 編碼存放,直接 grep 中文會找不到) |
| 附帶修正 | `.gitignore` 原寫法 `.chainlit/translations/` 會讓下一行的白名單失效,導致此檔無法 `git add`;改為 `.chainlit/translations/*` |
| PR | #9 |

### #5 回答混有簡體字與英文

| | |
|---|---|
| 問題 | 回答偶爾出現簡體字(如「通过」)或英文(如 disrespect) |
| 原因 | 系統規則沒有規定輸出語言;模型訓練語料以簡體為大宗,白話分析段落最容易漏 |
| 解決 | `app.py` 系統規則新增第 1 條:「一律使用臺灣慣用的繁體中文回答,不得出現簡體字,也不要夾雜非必要的英文詞彙」 |
| 效果 | 大幅改善,但**無法根除**(見第五節 #13) |
| PR | #11 |

### #6 深入問題答非所問

| | |
|---|---|
| 問題 | 問「為什麼」「有何意涵」時只複述情節,不做分析 |
| 原因 | 原規則「只回答你知道的內容」過度保守,模型不敢推論 |
| 解決 | 改寫系統規則第 3 條為「區分事實與詮釋」:情節、人物、時地依原文;遇「為什麼 / 意涵」類問題須就宋代社會、宗教、司法背景分析,並以「就此推測」等措辭標明為詮釋。原第 3 條放寬為「事實性內容只回答有把握的部分」 |
| 效果 | 會提出時代背景分析;但「就此推測」標記**時有時無** |
| PR | #11 |

### #2 無法接續追問(多輪對話)

| | |
|---|---|
| 問題 | 問「列出三則」後追問「第 2 則的詳細內容?」,系統答非所問 |
| 原因 | **兩個環節都缺前文**:① 送給模型的只有當下這句,沒有歷史;② 拿去查向量庫的也只有當下這句,「第 2 則」不含任何線索,查不到正確原文 |

**解決方式(兩件事都要做,少一個都不行):**

1. **對話歷史**:每答完一輪,把問答存進 session 的 `history` 清單;送給模型時透過 `MessagesPlaceholder("history")` 插在系統規則與問題之間。上限 20 則(`MAX_HISTORY_MESSAGES`),因為每輪都要重送、重付一次費用。

2. **追問改寫**:檢索前多呼叫一次模型,把追問補成完整問句,例如
   「第 2 則的詳細內容是什麼?」→「《夷堅志》中第 2 則**閉糴震死**的詳細內容是什麼?」
   **改寫後的句子只拿去查向量庫,不送給回答模型**(回答模型有歷史,自己看得懂)。

**實作上的兩個重要決定:**

- **改寫時不用 `MessagesPlaceholder` 傳歷史。** 第一版這樣寫,模型會順著對話直接作答,產出一大段答案當成檢索關鍵字。改為把歷史攤平成純文字貼進指令(`format_history_for_condense()`),並把「請改寫」放在最後緊貼生成點,才穩定。
- **長度防護。** 改寫結果超過 100 字(`MAX_SEARCH_QUERY_LENGTH`)視為失控,退回用原句檢索並記 warning。

| | |
|---|---|
| 驗證 | 列出三則後追問「第 2 則」,日誌可見改寫補上正確條目名,回答內容與原文相符 |
| 需求文件 | `docs/prd/PRD-多輪對話.md` |
| PR | #14 |

### #1 缺乏使用引導

分四個部分,皆在 PR #15(**尚未合併**)。

**(1) 首頁建議問題**
- 問題:首頁只有輸入框,使用者不知道能問什麼,把系統當關鍵字搜尋
- 解決:`@cl.set_starters` 顯示四則建議問題。題庫 `STARTER_POOL` 共 16 題,依問法分四類(主題檢索、單一條目、詮釋分析、人物主題),**每次開新對話各類抽一題並打亂順序**,保證四種問法都示範得到
- 注意:題庫裡的篇名都已核對語料確認存在;新增題目時也要先確認,否則點了查不到

**(2) 回答後的延伸問題**
- 系統規則新增第 6 條:回答結尾以「你可以接著問:」列出 2~3 個延伸問題
- 原本規定「離題時不給延伸問題」,但模型不理這條,且照樣給反而更好(能把話題引回本書),因此改規則配合此行為

**(3) 延伸問題改為可點擊按鈕**
- `split_followups()` 從回答結尾解析出延伸問題,掛成 `cl.Action` 按鈕,點擊即送出
- 為了讓「打字」與「點按鈕」共用同一套流程,回答邏輯抽成 `answer(question)` 函式
- **解析失敗時原樣保留純文字**,寧可沒有按鈕也不能吃掉內容
- **保留「你可以接著問:」標題**:曾經連標題一起刪掉,結果按鈕看起來像三行殘留文字
- 存進歷史的是移除延伸問題後的本文,避免干擾之後的追問改寫

**(4) 複製鍵移至右上角**
- 問題:加了延伸問題按鈕後,Chainlit 預設的複製鍵夾在按鈕之間,難以辨識
- 解決:新增 `public/custom.css`,並在 `.chainlit/config.toml` 啟用 `custom_css`。選擇器限定 `.ai-message` 內帶圖示的按鈕,延伸問題按鈕與使用者訊息不受影響

## 五、尚未解決的問題

四個 bug 的根源大多指向同一件事:**`gpt-4o-mini` 讀文言文的能力不足,指令遵循也不夠穩定。**

### #12 文言文主語誤判(P1,最嚴重)

系統會把故事人物張冠李戴,並順著提問的錯誤前提編造情節。已知兩例:

- **〈不孝震死〉**(`00000119.txt`):被雷擊死的是王三一本人,系統說成「他父親」。原文「父已復倒立矣」的「父」是從王三一之子的視角稱呼王三一
- **〈閉糴震死〉**(`00000118.txt`):囤糧遭天誅而死的是段二十六;段二十八是被誤劈(朱衣人曰「錯也」)且倖存。系統把兩人合併成一人

注意:首頁建議問題「雷擊報應的故事」**很容易帶出〈閉糴震死〉這個錯誤**,展示時要留意。

### #7 跨條目錯誤拼接(P1)

把不同段落的內容縫合,如「陸氏負約」「紙交子」兩例。原因是檢索回的 10 段沒有標題與出處,模型容易混用。規劃方向:改為「一則故事一段」並附篇名,重建向量庫。
注意:此法**解決不了 #12**(#12 的案例中篇名本來就在段落裡,仍然讀錯)。

### #13 繁體約束無法根除(P2)

系統規則只能降低機率。要根除得在輸出後加簡繁轉換(如 OpenCC),但可能誤改文言文的異體字與專有名詞,尚未決定。

### 「就此推測」標記不穩定(尚未開 issue)

#6 要求推論處須標明為詮釋,實測時有時無。

### #4 後台紀錄與帳號(P3)

尚未處理。最輕量的做法是啟用 `.env` 裡已預留的 LangSmith 追蹤,即可查閱所有提問與回答。

## 七、工作流程與文件

這個專案照以下流程管理修改,細節見 `docs/開發流程.md`:

```
開 Issue → 開分支 → 修改 → 本機測試 → 發 PR → 合併 → 更新 CHANGELOG → 部署 → 線上驗證
```

| 文件 | 用途 |
|---|---|
| `docs/開發流程.md` | 完整流程說明(分支命名、commit 格式、發版步驟) |
| `docs/測試/迴歸測試清單.md` | **改 prompt 或模型後必跑**,內含老師回饋的實際案例與歷次測試紀錄 |
| `docs/prd/` | 需求文件(目前有多輪對話) |
| `docs/adr/` | 重大技術決策紀錄(目前有部署架構) |
| `docs/templates/` | PRD 與 ADR 範本 |
| `CHANGELOG.md` | 已合併但未部署的修改累積在「未發布」區,部署時再切版本號 |

**兩個原則:**
- **改 prompt 之後一定要重測離題問題**(迴歸測試 C4)。放寬某條規則常會連帶鬆掉別的防線
- **懷疑回答有錯時,先回去翻原文**(`data_source/splitted/`)。#12 的兩個案例都是這樣發現的;也有一次以為是模型幻覺,查了才發現〈金四執鬼〉是真實條目
